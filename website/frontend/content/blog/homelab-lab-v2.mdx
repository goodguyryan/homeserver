## Private and Public Access Using IngressClass

One thing I wanted to figure out was how to separate public-facing applications from private applications, which are all accessible remotely. I decided on a dual IngressClass approach as it gave me a clean and declarative way to separate applications by access pattern.

For public-facing applications, I used the `nginx` IngressClass. These are applications that I am okay with exposing publicly, such as my personal website. Instead of exposing every service directly, the application traffic goes through the NGINX Ingress Controller, which acts as the entry point for public HTTP traffic.

For example, a public-facing application would use:

```yaml
ingressClassName: nginx
```

For private applications, I used the Tailscale Operator. These are applications that I only want to access privately, without exposing them directly to the public internet. Instead of going through the public ingress path, these applications use the `tailscale` IngressClass.

For example, a private application would use:

```yaml
ingressClassName: tailscale
```

In my case, this meant that something like my personal website could be exposed publicly, while internal tools like Headlamp could stay private and only be accessible through my Tailnet.

The Tailscale Operator also makes this feel quite clean because it handles the Tailscale side of exposing the private application. For private Ingress resources, it can create the required Tailscale proxy resources and route traffic from the Tailnet to the Kubernetes Service.

This was one of the parts that made the homelab feel more intentional. I was not just deploying random applications into a cluster, but also thinking about how each application should be accessed, and whether it should be public or private by default.
